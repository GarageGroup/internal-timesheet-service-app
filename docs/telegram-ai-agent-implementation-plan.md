# Telegram AI Agent: план реализации в Timesheet API

Дата: 25.09.2026. Статус: проект решения, не описание уже реализованной функциональности.

Текущий статус реализации и история изменений ведутся в [журнале прогресса](telegram-ai-agent-progress.md).

Документ предназначен разработчику и AI-ассистенту, который будет выполнять реализацию. Он фиксирует выбранный вариант: **Semantic Kernel внутри приложения API, Telegram-бот как транспорт, существующая привязка Telegram к корпоративному пользователю как основа авторизации**.

Создание этого документа не означает разрешения менять Azure, регистрировать приложения, назначать права или записывать данные в рабочую CRM. Такие действия выполняются отдельно согласованным владельцем инфраструктуры.

## 1. Результат, который нужно получить

Пользователь пишет боту, например:

> Спиши вчера два часа на проект X, комментарий «Разбирался с интеграцией».

Бот передаёт сообщение в API. Агент на Semantic Kernel находит доступный пользователю проект, уточняет неоднозначности, готовит операцию и показывает подтверждение. После подтверждения сервер выполняет операцию от имени связанного корпоративного пользователя и сообщает результат.

Поддержать только бизнес-возможности, необходимые для работы со списаниями времени: поиск и выбор проекта, получение периодов и тегов, чтение, создание, изменение и удаление списаний. Агенту не требуется предоставлять всё API. Профиль, подписки, уведомления, вход/выход и остальные несвязанные операции не регистрируются как AI tools. Авторизацию и выбор пользователя не отдавать модели.

Требования:

- Все обращения к модели, история диалога и вызовы AI-инструментов реализуются через Semantic Kernel. Модель размещена в Azure AI Foundry.
- Не просить пользователя входить через Entra при каждом сообщении. Первичная привязка выполняется через mini app; дальше используется серверная привязка учётных записей.
- Существующий mini app и его пользовательские HTTP-endpoint продолжают работать.
- Агент обращается к бизнес-обработчикам внутри API, без HTTP-запросов API к самому себе.
- Бот обращается к API по HTTPS с отдельной аутентификацией приложения.
- Изменяющие операции в первой версии требуют явного подтверждения. Это серверное правило, а не пожелание в prompt.
- Данные, инструменты и история разных пользователей изолированы.

## 3. Что подтверждено текущим кодом

### 3.1. API и CRM

- `src/app/Application/Program.cs` подключает endpoint проектов, списаний, тегов, подписок, профиля, входа/выхода и периодов; используется `UseJwtReader()`.
- `src/app/Application/Application/Application.cs` создаёт Dataverse-клиент через `UseTokenCredentialStandard()` и отдельный SQL-доступ к Dataverse. Конкретный credential в deployment нужно проверить отдельно.
- Входные контракты бизнес-операций и их реализации находятся в `src/endpoint/<Operation>/Contract` и `Endpoint`.
- В создании списаний и ряде других операций `CallerObjectId` устанавливается из пользовательского Entra object ID. SQL-запросы используют явные фильтры по пользователю.
- В рассмотренном пути обновления списания `BuildDataverseUpdateInput` не устанавливает `CallerObjectId`. При отсутствии нового проекта проверка проекта также не выполняется. Перед включением AI-изменений необходимо проверить фактическую авторизацию этой операции, включая CRM plugins. Само отсутствие поля ещё не доказывает уязвимость, но требует закрытого проверкой решения.
- Создание списания сейчас возвращает `Unit`, а не ID созданной записи. Для надёжного аудита/повторов потребуется внутренний результат с идентификатором либо проверяемый механизм поиска результата.

### 3.2. Привязка пользователя

- `src/endpoint/User.SignIn/Endpoint/Func/Func.Invoke.cs` проверяет Telegram `initData` и сохраняет запись в `gg_telegram_bot_users`.
- Используются поля `gg_bot_id`, `gg_chat_id`, связь `gg_systemuser_id`, признак `gg_is_user_signed_out`.
- Альтернативный ключ записи построен по CRM-пользователю и боту. Это **не гарантирует**, что один Telegram-пользователь не окажется связан с несколькими CRM-пользователями.
- В проверенном методе входа не обнаружена проверка свежести `auth_date`. Разбор `initData` необходимо сверить с официальным алгоритмом Telegram, включая декодирование параметров и получение `user.id` из JSON.
- Mini app использует MSAL и передаёт `Telegram.WebApp.initData` в `/timesheet/signIn` после корпоративного входа. Результат привязки должен быть явно обработан интерфейсом.
- Claims-сервис преобразует Entra object ID в CRM ID и добавляет `systemUserId`. Это два разных идентификатора.

### 3.3. Боты

- В Timesheet-боте `src/AzureFunc/Application/App.Bot.cs` уже есть цепочка middleware/commands и Durable Entity.
- `CultureMiddleware` получает пользователя по боту и чату, но отсутствие пользователя само по себе не останавливает дальнейшую обработку. Это не готовая защита агентского сценария.
- `WelcomeCommand.Parse` служит широким fallback. Обработчик обычного текста для AI должен быть зарегистрирован до него, но после явных команд.
- Текущий SignOut-обработчик связан с блокировкой бота; явную команду `/logout` нужно добавить отдельно.
- В SupportBot есть `UseAuthorization()`, OAuth callback и Blob-хранилище. Этот подход можно использовать позднее для входа прямо из чата, но внутренние сроки жизни авторизации используемых пакетов отдельно не подтверждены.

### 3.4. Не считать подтверждённым

По одному названию `UseJwtReader()` нельзя заключать, что весь необходимый набор JWT-проверок выполняется в приложении. До реализации проверить пакет, настройки и APIM: подпись, issuer, audience, lifetime и защиту обходного маршрута к backend. Политики APIM и CRM plugins не следует считать проверенными только по коду этих репозиториев.

## 4. Выбранная архитектура

```text
Telegram → проверенный webhook бота → бот с Managed Identity
                                      │ HTTPS + app-only token
                                      ▼
                             Внутренний Agent API
                                      │
                           проверка приложения и отправителя
                                      │
                        Telegram ↔ CRM ↔ Entra binding resolver
                                      │
                           доверенный UserExecutionContext
                                      │
                            Semantic Kernel → Azure Foundry
                                      │ native plugins
                                      ▼
                         существующие бизнес-обработчики
                                      │
                         Dataverse / SQL с user-scope проверками
```

Отдельно: `mini app → Entra login → существующий signIn → постоянная привязка`.

Здесь три независимых вида доступа:

1. **Бот → API:** токен приложения доказывает, что запрос отправил разрешённый бот-сервис.
2. **Telegram → корпоративный пользователь:** серверная привязка определяет, от чьего имени выполняется действие.
3. **API → Dataverse / Foundry:** собственные credentials сервиса. Они не передаются модели или в Telegram.

App-only токен сам по себе не подтверждает конечного человека. API доверяет разрешённому бот-сервису корректно передавать отправителя проверенного Telegram update. Поэтому безопасность webhook — обязательная часть этой архитектуры.

Это не OAuth On-Behalf-Of: пользовательский Entra access token не передаётся при каждом сообщении и не обновляется агентом. Привязка становится собственной долгоживущей сессией приложения. Истечение токена mini app не завершает такую сессию автоматически. Политики Conditional Access и повторного входа не следует считать автоматически перенесёнными на чат.

## 5. Модель идентичности и авторизации

### 5.1. Явно разделить идентификаторы

| Поле нового контекста | Значение | Источник |
|---|---|---|
| `BotId` | ID разрешённого Telegram-бота | Серверное сопоставление вызывающего приложения и бота |
| `TelegramUserId` | Числовой ID отправителя | `message.from.id` / `callback_query.from.id` проверенного update |
| `TelegramChatId` | Чат для доставки ответа | Проверенный update; не заменяет user ID |
| `CrmSystemUserId` | `systemusers.systemuserid` | Привязка в CRM |
| `EntraObjectId` | `systemusers.azureactivedirectoryobjectid` | CRM-пользователь из привязки |
| `TenantId` | Корпоративный tenant | Настройка сервера и проверенный токен приложения |
| `BindingVersion` | Версия/эпоха привязки | Серверное хранилище состояния привязки |

Существующий аргумент `SystemUserId` нельзя заполнять одинаково во всех обработчиках. Там, где контракт использует `[ClaimIn("oid")]`, передавать `EntraObjectId`. Там, где используется CRM-claim `systemUserId`, передавать `CrmSystemUserId`. Составить и проверить таблицу для каждого контракта перед написанием адаптера.

Не добавлять эти поля как параметры `[KernelFunction]`. Модель получает только бизнес-параметры, например дату, проект, длительность и комментарий. Контекст передаётся через DI и остаётся неизменяемым в рамках операции.

### 5.2. Алгоритм разрешения пользователя

1. Проверить приложение: tenant, audience, issuer, подпись, срок токена, app role и разрешённый client ID.
2. По идентичности приложения определить допустимый `BotId`; не доверять произвольному bot ID из запроса.
3. Для первой версии разрешить только private chat. Telegram ID хранить как `long` или каноническую десятичную строку, не `int`.
4. Найти активную привязку этого бота и `TelegramUserId`. Проверить, что историческое `gg_chat_id` действительно хранит user ID для существующих private-chat записей; не переносить это предположение на группы.
5. Ноль совпадений или signed-out → `UserNotLinked`, показать кнопку mini app. Несколько совпадений → `AmbiguousBinding`, ничего не выполнять.
6. Загрузить CRM-пользователя, проверить доступность/активность, наличие Entra object ID и принадлежность разрешённой организации согласно фактической модели CRM.
7. Создать серверный контекст и привязать к нему диалог, задания и подтверждения.
8. Перед любой мутацией повторно проверить актуальность привязки и права, даже если задание уже было поставлено в очередь.

На первом этапе не кэшировать положительную авторизацию надолго. При выходе, блокировке и перепривязке инвалидировать контекст, pending actions и доступ к прежнему диалогу. При необходимости кэша задать короткий TTL и механизм инвалидирования; одной очистки памяти одного instance недостаточно.

### 5.3. Первичная привязка и повторный вход

Начальный сценарий: неизвестный пользователь пишет боту → кнопка «Войти через приложение» → существующий MSAL login → проверенный `/timesheet/signIn` → следующее сообщение обрабатывается без повторного входа.

До использования привязки как основания выполнения команд:

- Проверять Telegram HMAC по официальному алгоритму, сравнение выполнять constant-time.
- Проверять `auth_date`: стартовое предложение — допустимый возраст 5 минут и небольшой clock skew. При просрочке предложить переоткрыть mini app.
- Корректно разобрать query-параметры и JSON `user`; не извлекать ID регулярным выражением из «последнего» параметра.
- Защитить привязку от replay и гонок. Повтор того же входа тем же пользователем может быть идемпотентным; изменение корпоративного владельца требует явного сценария перепривязки.
- Установить уникальность активного соответствия `(BotId, TelegramUserId)` и решить, разрешён ли одному CRM-пользователю более чем один Telegram-аккаунт. До решения безопасный default — один активный аккаунт на бота.
- Проверить существующие дубликаты до добавления ограничений. Не исправлять их автоматически угадыванием владельца.
- Добавить `/logout`, использующий тот же централизованный механизм отзыва, что и выход mini app.

«Не логиниться постоянно» не означает «никогда не проверять права». Перед production владелец безопасности должен утвердить максимальный срок привязки и условия step-up login. Если требуется регулярный MFA по корпоративным правилам, понадобится отдельный сценарий повторного Entra-входа.

## 6. Аутентификация бота в API через Entra

Предпочтительно использовать Managed Identity Azure-ресурса бота.

Инфраструктурные шаги:

1. Определить приложение Entra, представляющее API, и допустимый Application ID URI.
2. Добавить application app role, например `Timesheet.Agent.Invoke`, с allowed member type `Applications`.
3. Включить Managed Identity у бота и назначить её service principal эту роль на API. Managed Identity не требует отдельной регистрации клиентского приложения.
4. Настроить выдачу токена для scope `<ApiApplicationIdUri>/.default`.
5. В API создать отдельную политику для внутренних агентских маршрутов: роль плюс allowlist вызывающих приложений. Корректно учитывать `azp`/`appid` согласно версии токена, не путать client ID с object ID service principal.
6. Проверять фактический `aud` выдаваемого токена, а не предполагать, что он всегда совпадает со scope или URI. Не отключать audience validation ради запуска.
7. Не допускать, чтобы app-only `oid` был принят существующим endpoint как пользовательский oid. Агентские и пользовательские маршруты должны иметь различимые политики доступа.
8. Если аутентификация выполняется в APIM, закрыть прямой обход backend и формально определить доверие к передаваемой идентичности. Предпочтительно дополнительно валидировать токен в приложении.

Локально Managed Identity отсутствует. Использовать выделенный dev service principal с ролью на dev API и сертификатом либо локальным секретом вне git. Не создавать production bypass и не считать токен разработчика от Azure CLI эквивалентом app-only токена.

Telegram webhook должен проверять `X-Telegram-Bot-Api-Secret-Token` либо эквивалентную доказанную защиту на ingress. Azure Function key/APIM subscription key и проверка Telegram-источника — разные задачи. Не принимать сообщения об авторе из произвольного публичного JSON.

## 7. Размещение кода и повторное использование обработчиков

Предлагаемая структура, с адаптацией к соглашениям репозитория:

```text
src/service/Agent/
  Contract/       # DTO, статусы, интерфейсы orchestration/storage
  Core/           # identity, jobs, approvals, execution policy
  SemanticKernel/# kernel factory, plugins, инструкции модели
  Test/           # unit/integration tests с fake CRM/model
src/endpoint/Agent.* /
  Contract/       # HTTP-контракты по текущему стилю проекта
  Endpoint/       # submit, status, decision
  Test/
```

Имена здесь предлагаемые, не существующие. Не заводить новый framework для endpoint поверх существующего без необходимости.

### 7.1. Не дублировать бизнес-логику

Начать с фабрик зависимостей в `src/endpoint/*/Endpoint/*Dependency.cs`. Например, `TimesheetModifyDependency` сейчас создаёт internal `TimesheetModifyApi`, но наружу возвращает `TimesheetModifyEndpointSet`, а не `ITimesheetModifyApi`.

Нужный рефакторинг:

1. Внутри соответствующей сборки выделить фабрику/регистрацию, возвращающую публичный бизнес-контракт.
2. Существующий HTTP endpoint и агентский адаптер должны получать одну и ту же реализацию через эту фабрику.
3. Сохранить internal implementation, если нет причины расширять публичную поверхность.
4. Не использовать reflection, ручное создание endpoint или HTTP-запросы к самому себе для обхода DI.
5. Повторить для каждого подключаемого контракта, сохранив действующие HTTP-контракты и тесты.

Вызов обработчика напрямую обходит HTTP binding и middleware. Поэтому все обязательные проверки входа и прав должны быть в общем application/business слое либо в обязательном execution gateway. Проверка только в controller/endpoint недостаточна.

### 7.2. Контроль доступа к CRM

- В Dataverse write paths согласованно применять impersonation, где она поддерживается и требуется. `CallerObjectId` — Entra object ID, не CRM primary key.
- Проверить права сервисной учётной записи на impersonation и действующие ограничения Dataverse.
- Для SQL-чтений сохранить явные фильтры по текущему пользователю; наличие service credential не обеспечивает пользовательскую изоляцию автоматически.
- Для update/delete проверять доступ к целевой записи по ID, а не считать знание ID достаточным правом.
- Централизовать проверку, чтобы HTTP и агентский путь не расходились. Не включать AI update/delete до теста «пользователь A не может изменить запись B».

## 8. Semantic Kernel и покрытие API

### 8.1. Kernel и Foundry

- Использовать совместимые версии пакетов SK. В прототипе использовалась версия 1.80.0; перед переносом проверить актуальную совместимость и зафиксировать выбранные версии централизованно. Не обновлять все пакеты проекта попутно.
- Перенести проверенную конфигурацию подключения Foundry из прототипа. Endpoint/deployment и authentication должны соответствовать фактическому типу развёртывания, а не названию ресурса в Azure.
- Для native plugins OpenAPI plugin package не обязателен. `ChatCompletionAgent` также не обязателен, но допустим и удобен; первоначально нужен один агент, а не multi-agent orchestration.
- Создавать Kernel и плагины в scope выполнения с immutable пользовательским контекстом. Нельзя использовать singleton plugin с изменяемым CurrentUser.
- Общие HTTP/AI-клиенты можно переиспользовать согласно их требованиям thread safety.
- Историю диалога восстанавливать из persistent storage только после проверки владельца. Не хранить все диалоги исключительно в памяти процесса.
- Дату «сегодня», timezone и locale вычислять на каждом ходе; не один раз на старте процесса. Default timezone — `Europe/Moscow`, если пользовательская зона пока отсутствует.

Native plugin содержит `[KernelFunction]` и понятные descriptions параметров. Он переводит аргументы модели в существующий контракт, подставляет доверенный контекст и возвращает компактный структурированный результат. Модель не получает токены, connection strings, сырые stack traces или неограниченные CRM-ответы.

### 8.2. Матрица покрытия

Перед разработкой составить точный список методов по контрактам/OpenAPI и поддерживать его тестом или проверяемой таблицей. Исходная карта:

| Область существующего API | Инструменты агента | Режим |
|---|---|---|
| `Project.SearchSet` | Поиск доступных проектов | Чтение |
| `Project.GetSet` | Список проектов | Чтение |
| `Project.GetLastSet` | Недавние проекты | Чтение |
| `Timesheet.GetSet` | Списания за период | Чтение |
| `Timesheet.Modify`: create | Подготовка создания | Подтверждение → исполнение |
| `Timesheet.Modify`: update | Подготовка изменения | Подтверждение → исполнение |
| `Timesheet.Delete` | Подготовка удаления | Подтверждение → исполнение |
| `Tag.GetSet` | Доступные теги | Чтение |
| `Period.GetSet` | Доступные периоды | Чтение |
| `Agent.Profile.Get` | Диагностика привязки и авторизации | Временный отдельный endpoint, не AI tool |

Агент не получает «доступ ко всему API». Его allowlist ограничен операциями, которые непосредственно обеспечивают сценарии работы со списаниями времени. Добавление новой области API требует отдельного решения и обновления registry; наличие HTTP endpoint само по себе не делает операцию доступной модели.

Все операции должны иметь явную запись в registry: имя, контракт, read/write, политика доступа, необходимость подтверждения. Не определять безопасность по имени функции вроде `get` или `create`.

### 8.3. Поведение агента

- При нескольких подходящих проектах спросить пользователя, а не выбирать случайный.
- Переводить минуты в десятичные часы детерминированно в коде; соблюдать правила API, включая обязательный комментарий.
- Не придумывать project ID, записи, права, комментарии и успешные результаты.
- Названия проектов, CRM-комментарии и текст пользователя считать данными, а не системными инструкциями.
- Ограничить число модельных шагов, вызовов функций, размер результатов, timeout и расходы.
- Сводку старой истории делать через SK, но не считать её источником подтверждённых действий или авторизации.
- Для изменения нескольких записей показывать состав пакета. Без специально реализованной транзакции не обещать «всё или ничего»; отражать результат каждой операции.

## 9. Подтверждение изменений: вне контроля модели

Использовать двухфазную схему. Модель умеет вызвать `prepare_*`, но не имеет инструмента безусловного исполнения записи.

1. Агент готовит канонические аргументы; сервер проверяет их и сохраняет `PendingAction`.
2. В записи сохраняются owner, версия привязки, тип операции, точные аргументы, срок действия, версия/ETag целевой записи при наличии и correlation ID.
3. Бот показывает человеку понятный preview: проект, дата, часы, комментарий; для update — старое и новое значение; для delete — конкретная удаляемая запись.
4. Кнопки содержат только компактный opaque action ID/decision. Учитывать лимит Telegram `callback_data`; не помещать туда JSON или секрет.
5. На callback сервер снова проверяет приложение, отправителя, чат, owner, BindingVersion, срок и состояние действия.
6. Атомарно переводит `Pending → Executing`; повторный callback возвращает текущее состояние.
7. Исполняет сохранённые аргументы непосредственно через execution gateway, **без повторного решения модели**, что именно подтверждено.
8. Сохраняет бизнес-результат и только затем формирует сообщение об успехе. При конфликте или изменившихся данных требует нового preview.

Состояния: `Pending`, `Executing`, `Succeeded`, `Failed`, `Cancelled`, `Expired`, `Indeterminate`. Стартовый TTL подтверждения — 10 минут, настраиваемый.

Текст «да» в первой версии не исполняет произвольную последнюю операцию: бот просит нажать кнопку. Позднее текстовое подтверждение возможно только при однозначной серверной привязке к конкретному действию.

### 9.1. Контракт первого write-сценария

Первым реализовать создание одного списания. Update и delete подключать отдельными инкрементами после проверки ownership, impersonation и поведения при повторе.

`prepare_create_timesheet` доступен модели и принимает только бизнес-параметры: дату, выбранный проект, длительность и комментарий. Telegram identifiers, Entra object ID, CRM system user ID, action ID и срок действия не являются аргументами Kernel-функции. Их добавляет сервер из неизменяемого `AgentUserContext`.

Результат prepare содержит данные для отображения, но не выполняет CRM write:

- opaque `ActionId`;
- канонические дату, проект, длительность и комментарий;
- `ExpiresAt`;
- кнопки подтверждения и отмены.

Серверная `PendingAction` хранит дополнительно владельца (`BotId`, `TelegramUserId`, `TelegramChatId`, Entra object ID и CRM system user ID), тип операции, точные сериализованные аргументы, состояние, ETag, момент создания, срок действия, correlation ID и execution key. Отображаемый текст не является источником аргументов для исполнения.

Callback передаёт только `ActionId`, решение и фактические Telegram identifiers полученного update. После повторного разрешения пользователя API сравнивает владельца и атомарно переводит действие из `Pending` в `Executing`. Execution gateway строит `TimesheetCreateIn` из сохранённых аргументов и `AgentUserContext.EntraObjectId`, затем вызывает существующий `ITimesheetCreateFunc` напрямую, без HTTP к собственному API и без повторного обращения к модели.

### 9.2. Хранение и повторная доставка

Pending actions хранить отдельно от истории диалога, даже если используется тот же Azure Table account. Предлагаемая таблица: `TimesheetAgentAction`. Partition key должен начинаться с доверенного `BotId`, row key — с непрогнозируемого `ActionId`; проверка владельца обязательна независимо от ключа.

Стартовый TTL — `Agent:ApprovalTtlMinutes = 10`. Истёкшее действие не исполняется и переводится в `Expired`. Повторный confirm не вызывает CRM второй раз, а возвращает сохранённое состояние/результат. Cancel допустим только из `Pending` и также идемпотентен.

Создание списания нельзя автоматически повторять после timeout Dataverse. Пока не выбран CRM-side механизм идемпотентности, такое действие переходит в `Indeterminate`; пользователю предлагается проверить списания, а не повторить запись одной кнопкой. Это ограничение должно быть покрыто тестом до включения write feature flag.

### 9.3. Граница текущего инкремента

На 29.09.2026 определён только дизайн. Write plugin, action endpoint, callback бота, новая таблица и Azure-настройки ещё не создаются. Реализация начинается после ответа по `CallerObjectId` и выбора механизма идемпотентности создания.

## 10. HTTP-контракты и синхронное выполнение первой версии

Предлагаемые внутренние маршруты; итоговый нейминг согласовать с текущим endpoint framework.

### 10.1. Отправить сообщение

`POST /internal/agent/messages`, policy `Timesheet.Agent.Invoke`:

```json
{
  "telegramUpdateId": 123456,
  "telegramUserId": 123456789,
  "telegramChatId": 123456789,
  "text": "Покажи мои списания за вчера",
  "locale": "ru"
}
```

`BotId`, CRM ID, Entra ID и credentials не принимаются из этого DTO. Сервер определяет bot ID по вызывающему приложению. Locale не является security context.

Первая версия отвечает синхронно HTTP 200 после выполнения Semantic Kernel:

```json
{ "text": "За вчера списано 8 часов..." }
```

`telegramUpdateId` сохраняется в контракте как доверенный идентификатор исходного update и задел для будущей дедупликации. Сервер сам выбирает диалог по владельцу; если позднее появится conversation ID, проверять его owner.

### 10.2. Получить результат — отложено

Отдельный `GET /internal/agent/requests/{requestId}` в первой версии не нужен: готовый результат возвращает `POST /internal/agent/messages`. Status endpoint вводить только вместе с доказанной необходимостью фонового выполнения.

### 10.3. Подтвердить или отменить

`POST /internal/agent/actions/{actionId}/decision`:

```json
{
  "telegramUpdateId": 123457,
  "telegramUserId": 123456789,
  "telegramChatId": 123456789,
  "decision": "Confirm"
}
```

Разрешить только `Confirm`/`Cancel`. Аргументы бизнес-операции здесь не принимаются. Повторное подтверждение не создаёт новую операцию. Контракт подтверждения проектируется отдельно при включении writes; синхронный message endpoint не разрешает выполнять изменение данных без preview и явного подтверждения.

### 10.4. Ошибки

- `401`: отсутствующий/невалидный application token. Это проблема интеграции; не просить человека бесконечно входить в mini app.
- `403` + `UserNotLinked`: требуется привязка пользователя; показать кнопку входа.
- `403` + `UserDisabled` / `BindingRevoked`: доступ запрещён или отозван.
- `409` + `AmbiguousBinding` / `ActionConflict`: нужна коррекция привязки или новый preview.
- `404`: неизвестный либо не принадлежащий actor ресурс, без раскрытия чужого объекта.
- `429`: лимит запросов; вернуть retry guidance.
- Ошибки Foundry/CRM: безопасное объяснение и correlation ID, без секретов и ложного сообщения об успехе.

### 10.5. Решение по очереди

Для первой версии Azure Queue, request storage, outbox, dispatcher и worker не используются. Бот вызывает `POST /internal/agent/messages`, API синхронно разрешает пользователя, вызывает Semantic Kernel и возвращает текст. История диалога остаётся серверной и ограниченно хранится в Azure Table.

Для вызова Foundry задаётся конечный timeout. Бот не должен повторять запрос бесконечно и не должен сообщать об успехе при timeout или неопределённой ошибке.

Очередь рассматривается повторно только при наблюдаемой проблеме: Telegram/API timeout, необходимости переживать рестарты во время запроса, существенном росте нагрузки либо появлении долгих фоновых операций. Тогда возвращаются status endpoint, persistent request, transactional outbox и at-least-once worker с ETag-дедупликацией.

Последовательность одновременных сообщений одного диалога всё равно требуется контролировать. На первом шаге конфликт ETag истории возвращается как безопасная ошибка с просьбой повторить запрос, без автоматического второго вызова модели.

## 11. Идемпотентность CRM: обязательный отдельный этап

Запись состояния задания и изменение CRM не являются одной транзакцией. Возможен сценарий: CRM создала списание, процесс упал до записи `Succeeded`. Повторный запуск не должен слепо создать второе списание.

До включения создания выбрать и проверить один механизм:

1. Стабильный operation ID как уникальный ключ в Dataverse с проверкой владельца и результата; либо
2. Заранее назначенный ID записи, если конкретный клиент и операция это поддерживают, с чтением/проверкой после неопределённого результата; либо
3. CRM-side идемпотентная команда/транзакционный marker.

Если изменение схемы/клиента пока невозможно, результат timeout после отправки write переводится в `Indeterminate`. Автоматический повтор записи запрещён до сверки. Пользователю сообщить, что результат нужно проверить, а не предлагать немедленно повторить списание.

Для update использовать optimistic concurrency, если она поддерживается текущим клиентом, либо явную проверку версии и повторное подтверждение. Повтор удаления также обрабатывать осмысленно, различая уже выполненное действие и недоступную чужую запись.

Не обещать exactly-once на основании только Durable Entity, Queue или ETag в таблице. Они не делают внешний CRM side effect атомарным.

## 12. Изменения в Telegram-боте и mini app

В боте:

1. Проверить webhook authentication до обработки update.
2. Явные `/start`, `/help`, `/logout` и callback обработать раньше AI.
3. Добавить обработчик обычного текста перед `WelcomeCommand` fallback.
4. Для первой версии отклонять групповые чаты и неподдерживаемые вложения понятным сообщением.
5. Создать typed Agent API client с получением/caching application token через Azure Identity.
6. Передавать update ID и фактического отправителя, не данные из пересланного сообщения или текста.
7. При `UserNotLinked` показывать mini app; после успешного входа достаточно повторить исходный запрос. Автоматическое продолжение отложенного запроса можно добавить позднее, но не исполнять старые writes без preview.
8. Доставлять ответы и inline-кнопки, безопасно экранировать Telegram-разметку, делить длинные сообщения.
9. Подтверждать callback своевременно; повторная доставка callback не выполняет действие повторно.
10. Добавить `/new` для нового диалога, не для смены пользователя или сброса аудита.

В mini app:

- Дождаться результата `loadSignInRequest()` и показать «Аккаунт связан, можно вернуться в бот» только после успеха.
- Обработать просроченный initData, конфликт привязки и ошибки API.
- Выход должен вызывать единый механизм отзыва привязки и агентских действий.
- Не передавать user access token боту, в callback или в историю агента.

Вход непосредственно из чата через SupportBot-подобный OAuth callback — отдельный второй этап. При его добавлении обязательны state/nonce, одноразовое связывание callback с Telegram-инициатором и проверка безопасности redirect URI. Для первого запуска этот flow не нужен.

- Проверить/унифицировать authorization всех методов, особенно update и SQL read.
- Добавить cross-user тесты; существующие endpoint сохранить совместимыми.

Готово: обработчик можно вызвать из обычного кода с доверенным контекстом, права не зависят от наличия HTTP claim binding.

### Этап 3. SK только для чтения

- Подключить Foundry через SK, создать scoped kernel и native plugins чтения.
- Добавить лимиты, корректную дату/timezone, safe error mapping и изоляцию истории.
- Реализовать один синхронный message endpoint и бот-клиент; Queue, jobs/outbox/worker и status endpoint не добавлять без подтверждённой необходимости.

Готово: из Telegram доступны только необходимые для списаний read-возможности — проекты, периоды, теги и сами списания; неоднозначности вызывают уточнение; история между завершёнными запросами сохраняется. Профиль и прочие несвязанные области API не зарегистрированы как tools. Writes выключены.

### Этап 4. Подтверждения и надёжные записи

- Реализовать action registry, prepare/confirm/cancel и атомарные переходы состояния.
- Добавить защищённый исполнитель сохранённых аргументов.
- Закрыть CRM idempotency и неопределённые результаты; добавить идентификатор результата создания.
- Подключать create, update, delete, profile/subscriptions постепенно, но не считать задачу полной до всей согласованной матрицы покрытия.

Готово: никаких writes до подтверждения; повтор/чужой callback/выход/изменение привязки не приводят к записи; ошибки после CRM success не создают дубликат автоматически.

### Этап 5. Пилот и эксплуатация

- Включить для небольшого allowlist в тестовой среде, затем согласованного production-пилота.
- Проверить нагрузки, стоимость Foundry, лимиты Telegram, таймауты инфраструктуры и recovery.
- Настроить мониторинг очереди, ошибок авторизации, неопределённых writes и расходов модели.
- Документировать rollback: выключить writes/agent flag, запретить исполнение ожидающих действий, при необходимости отозвать app role. Автоматически «откатывать» уже созданные CRM-записи нельзя.

Готово: есть операторская инструкция, ответственный за ошибки и способ безопасно остановить агентский канал без остановки mini app.

## 15. Обязательные тесты

| Группа | Проверки |
|---|---|
| Application auth | Нет токена, неверная подпись/issuer/audience/tenant, истёкший токен, нет роли, чужой client ID; все отклоняются |
| Telegram ingress | Неверный webhook secret, подмена sender, group chat, повтор update |
| Linking | Неверный HMAC, старый auth_date, сломанный JSON, replay, два активных binding, конкурентная перепривязка |
| User isolation | Чужие request/action/conversation IDs недоступны; identity из prompt игнорируется |
| CRM permissions | A не читает/не меняет данные B; update без project не обходит проверку; SQL фильтры сохранены |
| Approval | До кнопки нет записи; другой sender не подтверждает; expired/revoked action не выполняется |
| Retry | Дубликат update/callback/queue; worker crash до/после CRM write; повтор Telegram send не повторяет CRM write |
| Concurrency | Два сообщения одного чата, два одновременных confirm, изменение записи между preview и confirm |
| AI | Неоднозначный проект, неправильные часы/дата, prompt injection в CRM-тексте, timeout/429 Foundry, лимит tool calls |
| Regression | Mini app login/signOut, все прежние HTTP-сценарии, команды бота и уведомления продолжают работать |

Unit-тесты выполнять с fake-моделью и fake CRM. Реальную модель тестировать отдельно на устойчивых сценариях без требования одинакового текста ответа. Реальные записи допускаются только в согласованной тестовой организации/под тестовыми пользователями; не использовать production для smoke writes по умолчанию.

## 16. Аудит, наблюдаемость и защита данных

Логировать структурированно: correlation/request/action ID, бот и actor, CRM user ID, имя операции, этап подтверждения, outcome, latency, token usage и безопасные коды ошибок. Аргументы писать минимально: комментарии и диалог могут содержать персональные/корпоративные данные.

Не логировать bearer tokens, initData, ключи и полные HTTP-body автоматически. Полный prompt/response tracing выключить по умолчанию; если он нужен для диагностики, использовать отдельный доступ, маскирование и короткий retention.

Разделить сроки хранения истории, технических jobs и аудита. Удаление истории не должно стирать обязательный аудит исполненных действий. Доступ к storage ограничить MI соответствующих сервисов. Перед запуском согласовать допустимость передачи CRM-текста в выбранное Foundry deployment и его регион.

## 17. Инструкция для будущего AI-ассистента

При поручении реализовать этот план:

1. Сначала перечитать актуальный код и локальные инструкции: пути и поведение могли измениться после даты документа.
2. Не считать предлагаемые классы, конфигурацию и endpoint существующими.
3. Начать с этапов 0–1, явно сообщить результаты проверки trust boundaries. Не маскировать отсутствие авторизации mock-пользователем вне тестов.
4. Работать небольшими проверяемыми изменениями. Не обновлять несвязанные зависимости и не переписывать endpoint framework.
5. Перед расширением на бот/mini app проверить их git status и согласованный объём работ. Не менять SupportBot только потому, что он используется как референс.
6. Не читать/выводить реальные секреты ради документации. Не коммитить credentials.
7. Не выдавать HTTP/API success за доказательство фактического CRM-результата без проверки контракта.
8. После этапа запускать относящиеся к нему тесты и сборку; сообщать отдельно, что проверено автоматически, вручную, а что требует Azure/test CRM.
9. Не включать production feature flags, не назначать app roles и не выполнять migrations/реальные writes без отдельного разрешения.
10. Обновить этот документ по фактическим решениям, включая пути, конфигурацию, настройку локального запуска и оставшиеся ограничения.
11. Соблюдать существующий функциональный стиль проекта: использовать `AsyncPipeline`/`Pipeline` для orchestration, преобразований, вызовов зависимостей и обработки `Result` везде, где это соответствует имеющимся аналогам. Это правило распространяется на production-код, dependency composition и тесты; императивный код допустим только там, где pipeline делает стандартный framework flow менее ясным.
12. Перед созданием или изменением модуля выбрать ближайший существующий аналог и точно повторить его структуру каталогов и partial-файлов. В частности, реализация функции endpoint располагается в `Endpoint/Func`, её сценарии — в `Func.Invoke.cs`, а тесты — в `Test/Test.Func` с базовым partial-классом и отдельными файлами сценариев.
13. Диагностический endpoint `Agent.Profile.Get` сохранять для демонстрации сквозной авторизации до отдельного указания владельца проекта. Не удалять его при появлении основного `/internal/agent/messages`; удалить только после явного согласования.
