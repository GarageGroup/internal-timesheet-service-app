# Telegram AI Agent: обзор решения для руководителя

Последнее обновление: 30.09.2026.

## Результат

В тестовый контур Timesheet добавлена возможность обращаться к системе обычным текстом через
Telegram-бота. Пользователь пишет, например, «какие проекты мне доступны для списания?», бот безопасно
передаёт запрос в Timesheet API, а AI-агент на базе Semantic Kernel выбирает разрешённые операции API
и формирует ответ.

Агент умеет читать данные, а также подготавливать создание, изменение и удаление списаний. Любая
операция записи сначала показывает пользователю серверный preview и выполняется только после явного
нажатия кнопки подтверждения. Отмена не изменяет CRM, повторное или конкурентное подтверждение не
может повторно выполнить операцию.

Проверена полная цепочка:

```text
Telegram
  -> test Telegram bot
  -> Managed Identity access token
  -> отдельный маршрут APIM
  -> Timesheet API
  -> серверная привязка Telegram-пользователя к CRM-пользователю
  -> Semantic Kernel
  -> Azure AI Foundry / gpt-5-mini
  -> разрешённый инструмент API
  -> для write: серверный preview и кнопка подтверждения
  -> Action Table и атомарное исполнение сохранённых параметров
  -> ответ пользователю в Telegram
```

## Почему агент размещён внутри Timesheet API

Semantic Kernel и инструменты агента размещены в API, а Telegram-бот оставлен тонким транспортным
слоем. Бот принимает update, получает app-only токен, вызывает один внутренний endpoint и возвращает
готовый текст.

Такой подход выбран по следующим причинам:

- бизнес-операции, CRM-контекст и проверки прав остаются рядом с существующим API;
- Telegram-бот не получает прямой доступ к Dataverse и Foundry;
- инструменты переиспользуют существующие application-модули, `AsyncPipeline`, `Dependency` и принятую
  структуру проектов;
- модель не знает внутренних credentials и не может самостоятельно вызывать произвольные URL;
- один endpoint `POST /internal/agent/messages` скрывает внутреннее количество инструментов;
- в будущем тот же agent-слой можно использовать из другого доверенного канала.

## Как используется Semantic Kernel

Для каждого сообщения API создаёт scoped Kernel, подключённый к deployment модели в Azure AI Foundry.
В Kernel регистрируется только явно разрешённый набор native plugins. Semantic Kernel отвечает за:

- передачу системной инструкции и ограниченной истории диалога;
- автоматический выбор подходящей функции;
- преобразование аргументов модели в типизированные входы;
- вызов разрешённого application-кода;
- передачу результата функции обратно модели;
- получение итогового ответа пользователю.

Модели не предоставляется «всё API». В agent surface входят только функционально необходимые операции.
Временный диагностический `/profile` удалён после завершения сквозной проверки авторизации. Профиль
не является инструментом модели и не входит в agent API.

Агенту доступны функционально необходимые блоки списания времени: поиск доступных проектов,
получение тегов, чтение timesheet и подготовка создания, изменения или удаления. Модель не выполняет
запись напрямую и не получает функции confirm/execute. Она может подготовить не более одного действия
за ход; точные параметры сохраняются API и после подтверждения исполняются без повторного решения модели.

## Новая схема авторизации

### Проблема прежней схемы

Mini App авторизует человека интерактивно через Entra ID. После входа сервер сохраняет привязку между
Telegram-пользователем и корпоративным CRM-пользователем. Но обычное сообщение Telegram не содержит
Entra access token пользователя. Требовать интерактивный вход перед каждым сообщением было бы неудобно
и не соответствовало бы модели работы бота.

Также API и бот ранее могли использовать общую user-assigned Managed Identity. В таком случае API не
может надёжно отличить вызов самого API от вызова Telegram-бота по claim `appid`/`azp`.

### Выбранное решение

Авторизация разделена на две независимые части:

1. **Авторизация приложения.** Telegram-бот вызывает agent API от собственной system-assigned Managed
   Identity. Для API создана отдельная Entra App Registration и application role
   `Timesheet.Agent.Invoke`. Только Managed Identity бота получила эту роль.
2. **Определение человека.** Бот передаёт фактические Telegram user/chat identifiers. API не считает их
   доказательством личности, а проверяет ранее созданную серверную привязку Telegram ↔ CRM. Из неё API
   получает доверенный `AgentUserContext` с CRM user ID и Entra object ID.

Таким образом, повторно входить через Entra ID перед каждым сообщением не нужно. Интерактивный вход в
Mini App нужен для первичного создания или восстановления привязки. После этого бот подтверждает свою
идентичность Managed Identity, а API самостоятельно разрешает пользователя по серверным данным.

### Что именно проверяет API

Для `/internal/agent/*` используется отдельная JWT Bearer схема. API проверяет:

- подпись токена и tenant;
- audience отдельной App Registration agent API;
- issuer v1 или v2 конкретного tenant;
- наличие application role `Timesheet.Agent.Invoke`;
- client ID вызывающей Managed Identity в allowlist;
- серверное сопоставление client ID с конкретным Telegram `BotId`;
- наличие активной Telegram/CRM-привязки и состояние CRM-пользователя.

`BotId` не принимается из JSON. Он формируется API из доверенной конфигурации вызывающего client ID.
Это не позволяет клиенту подставить идентификатор другого бота.

### Зачем одновременно JWT и клиентский сертификат APIM

App Service API принимает backend-запросы только с требуемым client certificate. Поэтому бот вызывает
API через отдельный APIM route:

- APIM предъявляет backend-сертификат App Service;
- исходный Bearer token Managed Identity сохраняется;
- API самостоятельно проверяет JWT, роль и allowlist.

Сертификат подтверждает разрешённый сетевой посредник, а JWT подтверждает вызывающее приложение. Эти
механизмы решают разные задачи и не заменяют друг друга.

Существующую policy Mini App не ослабляли. Для agent-вызовов создан отдельный APIM API, поскольку у
Mini App и server-to-server вызовов разные модели доверия.

## Доступ API к CRM, Foundry и Storage

Входящий токен бота не используется для обращения к Dataverse. Как и раньше, API выполняет CRM-запросы
собственной сервисной учётной записью и применяет разрешённый сервером пользовательский контекст.

Для новых Azure-зависимостей API использует свою user-assigned Managed Identity:

- роль `Cognitive Services User` на Foundry resource — вызов модели без API key;
- роль `Storage Table Data Contributor` на Storage Account — чтение и запись истории без connection
  string или account key.

Credentials бота для входа в API, credentials API для Foundry/Storage и credentials API для CRM имеют
разные назначения. Даже если часть из них технически обслуживается Azure Identity, права выдаются
минимально и на разные scopes.

## История диалога и конкурентность

Ограниченная история хранится в Azure Table `TimesheetAgentConversation`. Ключ строится из доверенных
`BotId`, Telegram user ID и chat ID. Клиент не передаёт историю самостоятельно.

Запись использует ETag optimistic concurrency. Если два сообщения одного диалога обрабатываются
одновременно, API не перезаписывает историю молча, а возвращает конфликт. Количество сохраняемых
сообщений ограничено конфигурацией.

## Почему первая версия синхронная

Первоначально рассматривались Queue, persistent request, worker, status polling и transactional outbox.
Для текущего короткого интерактивного сценария они заметно усложняли архитектуру и эксплуатацию. Поэтому
выбрана схема:

```text
bot -> POST /internal/agent/messages -> Semantic Kernel -> response / prepared action
bot -> POST /internal/agent/actions/{actionId}/decision -> Dataverse
```

Очередь будет возвращена только при подтверждённой необходимости: стабильные HTTP timeout, длительные
операции, высокая нагрузка, необходимость гарантированного восстановления после рестарта либо фоновые
write-операции.

## Модель и регион

В test используется:

- Foundry resource/project `ai-timesheet-test` в `West Europe`;
- модель `gpt-5-mini`, версия `2025-08-07`;
- deployment `GlobalStandard`, capacity 10K TPM.

`gpt-5-mini` выбрана как баланс качества, задержки и стоимости для tool calling. На момент настройки в
подписке была доступна квота этой модели, тогда как для `gpt-5.4-mini` квота была нулевой.

Важно: `GlobalStandard` может обрабатывать inference вне региона ресурса. Перед production необходимо
согласовать допустимость передачи названий проектов, комментариев и других CRM-данных. Если обработка
должна оставаться в ЕС, потребуется совместимый `DataZoneStandard` deployment и соответствующая квота.

## Что уже проверено

- основной message flow подтверждает цепочку MI → Entra app role → APIM certificate → API → CRM binding;
- запросы без корректного токена отклоняются;
- обычный Telegram-текст маршрутизируется в `/internal/agent/messages`;
- API получает доверенный пользовательский контекст;
- Semantic Kernel вызывает Foundry и выбирает разрешённый read/write-prepare инструмент;
- пользователь получает корректный ответ о доступных проектах;
- история диалога доступна через Azure Table;
- Mini App flow продолжает работать независимо от agent flow.
- create, update и delete проходят общий серверный prepare/confirm/cancel flow;
- Cancel для каждой операции не изменяет Dataverse;
- Confirm создаёт, изменяет или удаляет ровно сохранённое действие;
- полный write-контур проверен реальными Telegram callback и записями test Dataverse.

## Текущие ограничения и следующий этап

- `CallerObjectId` унифицирован для create/update/delete и берётся только из доверенного
  `AgentUserContext.EntraObjectId`; решение проверено в test;
- update пока не может явно очистить комментарий: пустое значение означает «не изменять»;
- при неопределённом результате Dataverse action становится `Indeterminate` и автоматически не
  повторяется; до production нужна операторская reconciliation-процедура;
- требуется согласовать бизнес-дату между `Europe/Moscow` и UTC-валидацией Dataverse;
- необходимо исключить Telegram bot token из Application Insights URL telemetry и после исправления
  ротировать test token;
- голосовой ввод развёрнут и проверен в test: безопасный поток `Telegram voice → APIM file proxy → Semantic Kernel Audio-to-Text → существующий gpt-5-mini agent` использует тот же message endpoint, identity boundary, tools и подтверждения; read-only, preview, Cancel и Confirm smoke tests успешны, исходное аудио не сохраняется;
- для agent message operation в test задан отдельный APIM backend timeout 60 секунд; decision operation и остальные API не затронуты;
- перед production нужны security review, data residency decision, нагрузочная проверка, мониторинг
  latency/429/стоимости и формализованный rollback.
